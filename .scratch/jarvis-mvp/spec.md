# Jarvis MVP: private German desktop conversations

Status: ready-for-agent

## Problem Statement

The user wants to ask short questions while working on a CachyOS desktop, hear intelligible German answers, and ask contextual follow-ups without repeatedly activating an assistant. Cloud speech and inference would expose private conversations, and GPU speech processing would compete with the local language model for limited VRAM.

The assistant must make its listening boundaries clear, stop when requested, and recover from desktop audio or model failures without replaying old work. Unreliable wake detection must not prevent a useful manual-activation release. Claims about German recognition, speaker operation, and response speed must be supported by measurements on the actual machine.

## Solution

Build a local-only German voice assistant that runs as user-session background services on CachyOS with KDE Plasma and PipeWire. The first release primarily supports a headset and useful offline questions. A single shortcut press or CLI trigger starts listening after an activation sound; silence finishes the utterance. A validated German-capable “Hey Jarvis” model can additionally enable hands-free activation, including a command spoken immediately after the phrase.

Jarvis gives concise spoken German answers and keeps temporary conversation context. After a reply completes or is stopped, the user has a configurable 20-second follow-up window. Standalone voice control phrases distinguish stop playback, end conversation, retry request, and conversation extension. Manual activation during generation or playback cancels that operation and accepts a replacement question. Locking or muting stops capture and playback and clears the conversation.

Five-minute conversation expiry finishes the current turn, then asks for an explicit extension. Text answers are available through deliberate temporary CLI access for content such as code and tables. Capability health, installation instructions, reproducible benchmarks, and a release checklist identify what passed, failed, or remains unvalidated. Manual-only operation is an accepted MVP mode; a useful release with documented gaps is distinct from a release that has passed every P0 requirement.

## Implementation Decisions

- **Scope and target:** Implement the P0 baseline through milestones M0–M4. Target CachyOS, KDE Plasma, PipeWire, Ryzen 5 5600, Radeon RX 9070 XT with 16 GB VRAM, and 32 GB RAM. The first acceptance setup is a headset. Support a single active user/conversation and do not claim general Linux support.
- **Process boundaries:** A Node.js/TypeScript conversation core owns deterministic control, session context, configuration, policy, cancellation, observability, and the Ollama gateway. A Python audio service owns capture/output, conversion/resampling, pre-roll, wake detection, VAD, recognition, synthesis, and playback reporting. Ollama remains an independently managed local inference service. Only the core can trigger tools.
- **Primary test interface:** Expose conversation behavior through the core's public orchestration interface. Supply service/desktop events and a controllable clock at this boundary; observe requested audio/inference operations, public status, text answers, and permitted context. Prefer this one behavioral seam over exposing individual state-machine helpers or duplicating business rules in adapters.
- **Local transport:** Use a versioned, documented, bidirectional Unix-domain-socket protocol with runtime-validated TypeScript schemas and Python-compatible contracts. Carry control events and bounded binary/audio frames or a separately negotiated local audio channel. Include readiness, errors, operation cancellation, playback completion/delivery reporting, reconnect behavior, and backpressure. Associate asynchronous results with the operation they belong to so canceled results cannot affect another turn. No public listener or cloud fallback is introduced.
- **Audio policy:** Use a proven PipeWire or PipeWire-compatible PulseAudio client with stable device selection and explicit mono PCM conversion/resampling. Internal recognition audio defaults to 16 kHz, which need not match the device or voice rate. Keep the rolling pre-roll bounded; default to 750 ms within the ADR's 500–1000 ms range. Default VAD end silence is an illustrative 350 ms and maximum utterance duration is 30 seconds; thresholds require measurement.
- **Speech engines:** Start with Silero VAD on CPU, a replaceable sherpa-onnx recognizer interface, and resident German Piper synthesis, initially Thorsten medium/high. Compare German-capable Parakeet TDT v3 INT8 with a small true-streaming alternative. Do not label endpointed/chunked recognition as genuine partial streaming. Exact model selections remain provisional until benchmarks, licensing, provenance, and runtime compatibility are verified. Speech inference allocates no dedicated GPU VRAM by default.
- **Language model:** Use streamed Ollama generation over loopback with configurable model and settings, initially an illustrative maximum context of 8192 tokens. Benchmark local configurations for German accuracy, conversational usefulness, and latency. Streaming generation does not imply early speech: sentence/chunk speech before full generation is deferred to P1.
- **Manual activation:** One shortcut press or CLI trigger starts a turn without holding a key. Play a configurable short activation sound, enabled by default, and begin manual listening after it finishes. Silence endpoints the utterance. During thinking or speaking, the same activation action cancels the current operation and accepts a replacement question after acknowledgment. Manual activation is permitted only when capture is not inhibited.
- **Experimental wake activation (user decision, 2026-10-20, #13):** Enable the pinned local CPU “Hey Jarvis” candidate by default in real voice mode, threshold 0.2; explicit disable selects manual-only idle. Accept measured 23/30 (76.7%) held-out headset recall as an experimental limitation, without passing the original >=95% full-validation gate. Preserve bounded pre-roll and trailing speech continuously without acknowledgment clipping. Missing artifacts/runtime/device capabilities select manual fallback where permitted; no startup downloads. Health distinguishes enablement/readiness/experimental quality. Privacy/cancellation requirements remain mandatory.
- **State and capture conditions:** Use idle, listening, thinking, speaking, follow-up, and awaiting-extension conversation states. Lock and mute are separate capture-inhibiting conditions with priority over every active state. Idle permits only configured wake detection and bounded overwritten pre-roll, never ambient STT or LLM requests. Manual-only idle waits for deliberate activation.
- **Follow-up window:** Start the default 20-second window after playback completes or is stopped, never after transcript completion. Permit configuration from 5 to 60 seconds. Speech begun before the deadline has a bounded recognition-completion allowance. Noise or an empty result leaves the original deadline in force and never grants a new window; if it has expired, close. Document and test the selected allowance rather than inventing a validated duration. A valid turn receives its next window after its reply finishes.
- **Voice control phrases:** Deterministically recognize a small set of standalone commands before LLM interpretation. “Stopp” stops the current spoken reply and opens follow-up without closing context. “Danke Jarvis, das war's”, “Gespräch beenden”, and “Gute Nacht Jarvis” close the conversation. “Weiter” is a conversation extension while awaiting extension; “Noch einmal” is a retry request while a failed question remains available. A quoted word or a word embedded in a question does not trigger a control action.
- **Voice stop versus barge-in:** Spoken stop during playback is a separate P0 capability requiring bounded microphone processing and independent acoustic validation. Half-duplex normal conversation is permitted, but does not establish voice-stop correctness. Manual cancellation is available when voice stop is unreliable; that release records an FR-09 gap. General voice barge-in that redirects to a new utterance remains P1, distinct from deliberate manual replacement.
- **Cancellation and delivered reply:** Cancel active recognition, generation, synthesis, or playback as appropriate and ignore late results from canceled work. Preserve completed exchanges and the delivered portion of an interrupted reply. Exclude unheard generated remainders and unanswered canceled questions from future context. The audio boundary must provide evidence of playback delivery; precise tracking accuracy is validated with the chosen adapters rather than inferred from text generation or synthesis completion.
- **Lock and mute:** Either immediately stops microphone capture and playback, cancels work, closes the conversation, and clears temporary audio and context. Respect hardware mute. Unlock or unmute restores activation readiness only if all capture inhibitions have cleared. Neither resumes a previous turn or conversation.
- **Conversation expiry:** Default to a configurable five-minute duration allowance. When it expires, finish the current turn, then issue a brief extension prompt instead of starting another normal follow-up window. Expiry between turns prompts immediately. After the prompt finishes, allow 20 seconds for extension/end commands only. “Weiter” grants five more minutes with existing context; silence closes. Separate watchdogs handle stalled operations and may interrupt them; normal expiry does not cut off healthy speech.
- **Memory and output:** Keep context and temporary audio in memory per conversation. Clear them, along with service-side text answer access, on closure, lock, or mute. Default to concise German; expand on request. Summarize code/large tables aloud and indicate deliberate CLI access to the current session's text answer. Do not persist text answers or add them to routine logs. Generated but unheard remainders do not enter follow-up context merely because they are available as text. Persistent memory is excluded.
- **Failure and health:** Report concrete capabilities, including manual activation available when wake detection is missing, and voice conversation unavailable when STT or TTS is unavailable. On an active-turn failure, give one brief indication where possible, preserve context while the session remains open, and wait for a retry request or new question. Recovery alone does not replay work. Avoid repeated audible errors at idle; expose diagnostics through the CLI. Recover from device loss, hotplug, audio backend reconnect, suspend/resume, and service restart or report degraded operation without busy loops or accidental recording.
- **Service lifecycle and configuration:** Run the two project services as systemd user units after desktop audio is available, with failure restart limits and readiness/health reporting. Linger is disabled by default. Use schema-validated configuration and standard XDG locations for configuration, state, and user-runtime sockets. Restrict the socket to the user through 0600 permissions or equivalent directory protection. Expose devices, model identifiers, endpoint, thresholds, timers, utterance/context limits, interaction sounds, and disabled feature flags with documented defaults.
- **Security and tools:** The MVP has no external data adapters or side-effecting integrations. Keep inference local and tools disabled; enforce policy in the core rather than trusting model text. Arbitrary LLM output never becomes shell execution. Retain a modular policy/registry boundary for future authorized adapters without implementing speculative network tools.
- **Reproducibility and diagnostics:** Use Node and Python lockfiles, a project Python environment, and a model manifest with exact model names/revisions/checksums plus licensing/provenance. Provide content-free structured health/timing/error logs with bounded growth and measurements for wake, speech endpoint, STT final, LLM first token, first TTS audio, playback start/end, and interruption. Bound queues, utterances, history, pre-roll, and stalled work.
- **Delivery sequence:** M0 provides runnable core/audio skeletons, protocol, config validation, manifest structure, diagnostics, deterministic mocks, mock Unix-socket handshake, and development checks without hardware. M1 integrates local capture, VAD, recognition, synthesis, and a recorded German fixture. M2 implements the conversation behaviors at the primary public seam. M3 integrates desktop activation, user services, lock/mute, recovery, and capability health, with optional validated wake mode. M4 publishes reproducible benchmarks, stability checks, and requirement-level release evidence. Do not front-load speculative model integrations into M0.

## Testing Decisions

- **Good tests assert external behavior:** Drive public inputs and inspect observable operations, capability status, delivered output, text access, and the context supplied to a subsequent inference request. Avoid assertions about private state layout, helper invocation counts, or duplicated implementation logic. Use deterministic adapters and a fake clock, not sleeps or live models, for conversation rules.
- **Prior art:** There is no application implementation or existing test suite in the project. The PRD and ADR define the testing strategy, but do not establish proven test infrastructure. Introduce one primary public conversation-core seam; keep adapter-specific checks at public contracts instead of creating many business-logic seams.
- **Conversation flow:** Verify manual activation, acknowledgment completion, utterance endpoint, inference, synthesis, playback, contextual follow-up, and timeout/explicit end. When wake mode is configured, scripted wake plus command preserves the immediate question. Simulated events prove orchestration only, not acoustic recognition.
- **Timing:** With a fake clock, assert no follow-up countdown while an answer is still playing; timeout begins on completion or stop. Cover the configurable window, speech near the deadline, bounded recognition completion, empty/noise results retaining the original deadline, and no indefinite renewal from repeated noise. Cover five-minute expiry during a turn and between turns, extension prompt playback, the 20-second extension/end-only window, explicit renewal with context, and silence cleanup. Test stalled-operation recovery separately from normal expiry.
- **Commands:** Exercise stop playback versus end conversation versus manual replacement, all documented German end phrases, extension/retry only in their appropriate contexts, and ordinary questions containing or quoting control words. Prove that model output does not override explicit control.
- **Cancellation and context:** Cancel during thinking and playback, then inject stale recognition, inference, synthesis, and playback events. Assert no late reply or disruption of a newer turn. Use known playback delivery reports and inspect the next inference context to verify preservation of delivered reply and completed exchanges, exclusion of unheard remainders, and removal of unanswered canceled questions. Confirm deliberate text access cannot accidentally promote undelivered speech into follow-up context.
- **Privacy and capability behavior:** Through the public seam, prove idle does not request STT/LLM, lock/mute stop capture/playback and clear context/text access, clearing one inhibition leaves the other effective, and readiness restoration does not replay work. Exercise missing wake, STT, TTS, and Ollama capabilities and a single active-turn error indication. Verify recovery requires a retry request or new question, and routine logs exclude fixture content.
- **Transport and foundation:** Contract-test the real local socket between mock core/audio processes for typed handshake/readiness, invalid or incompatible messages, cancellation, disconnect/reconnect, bounded queues/backpressure, and restrictive local access. Verify schema-invalid configuration produces a useful diagnostic. These support the primary behavioral seam rather than duplicating its scenarios across both languages. M0 must build and pass its hardware-free checks locally and in CI.
- **Local integration:** With consented or synthetic recorded German audio, test recognition and Piper output through their public adapters. Use a loopback Ollama fake server for repeatable streamed answers, error, and cancellation behavior. Verify selected real adapters can transcribe the predefined recording, synthesize a German reply, and play it on the chosen device. Model-backed tests are separate from fast deterministic conversation tests.
- **Hardware acceptance:** On the target desktop, validate global single-press activation, audible acknowledgment timing, hardware mute, KDE lock/unlock, microphone loss/reconnect, suspend/resume, startup/restart, chosen output devices, and no idle transcription. Verify no capture while locked/muted with real devices. Publish headset and speaker results separately. Measure voice-stop recognition and false stops during playback independently from general barge-in; manual cancel cannot establish spoken-stop acceptance.
- **Wake gate:** If hands-free activation is claimed, use the actual microphone and a defined German wake-plus-command set to measure recall, clipping, transition latency, and false accepts during representative noise, TV/music, and assistant playback. Verify model licensing, provenance, runtime compatibility, and reproducible installation. The user-approved #13 experiment is enabled by default at 0.2 with 76.7% recall; this exception does not change the original full-validation criteria or privacy/cancellation requirements. Manual-only activation remains available through explicit disable and can pass the MVP activation gate independently.
- **Quality and performance:** Compare at least two German-capable STT configurations using a fixed corpus of at least 30 utterances, including common English technical terms. Document quality gates and errors rather than inventing benchmark results. Compare local LLM settings for conversational usefulness and resource/latency behavior. For at least 30 warm short local queries without tools, report speech-end-to-audible-answer p50/p95 against initial targets of at most 1.5 seconds and 3 seconds respectively. Record model revisions, quantization/settings, device, and CPU/GPU/Ollama state; include cold/warm and quiet/noisy conditions. Report idle/concurrent CPU and RAM plus dedicated speech-service VRAM, expected to be zero by default.
- **Stability and offline operation:** Complete a two-hour idle soak, a 30-turn follow-up test, extended sessions with explicit renewal, service recovery, and suspend/resume. Repeat representative interactions with external network connectivity disconnected and locally installed models. Establish bounded queues, buffers, logs, and capture behavior under failures. Publish a reproducible regression baseline and known gaps.
- **Release acceptance:** Map the checks to PRD requirements FR-01 through FR-25, keeping FR-15 through FR-18 deferred to P1. Record passed, failed, or unvalidated per applicable requirement and test setup. Local inference, idle privacy, bounded capture, and cancellation are mandatory. A useful release may carry a disclosed FR-09 voice-stop gap, but never claim all P0 requirements passed. Missed latency targets require evidence and review; targets may be revised transparently and a missed target is not marked passed.

## Out of Scope

- General full-duplex voice barge-in, default speaker echo cancellation before acoustic validation, and early sentence/chunk TTS while LLM generation is still in progress.
- A KDE tray UI, graphical model picker, or calibration UI as a requirement for operation.
- Internet-enabled quote/weather/data adapters, claims of current market information from LLM knowledge, Home Assistant, desktop actions, arbitrary shell commands, trades, purchases, and other side effects.
- Cloud LLM, STT, TTS, or wake-inference fallback; audio uploads; always-on transcription; ambient conversation archives.
- Persistent conversation memory, voice biometrics, speaker profiles, person recognition, and multiple simultaneous users.
- Promised German dialect quality, prolonged dictation, multilingual switching, cross-device operation, distributed deployment, root services, or broad Linux distribution support.
- Guarantees of perfect wake detection, spoken stop, speaker barge-in, or unmeasured hardware performance.
- Custom acoustic-model training pipelines and third-party training services as part of the MVP implementation.
- Implementation work, automatic ticket decomposition, or additional triage performed merely by publishing this spec.

## Further Notes

- This spec synthesizes the 24 product decisions accepted during the design interview and the final shared-understanding confirmation. It preserves the accepted architecture and uses the domain glossary vocabulary.
- Sources: [PRD v0.2](../../docs/PRD-jarvis.md), [ADR-0001](../../docs/ADR-0001-architecture.md), and [domain glossary](../../GLOSSARY.md).
- **Current state:** Only product/domain documents and agent-skill configuration exist. There is no application code, dependency setup, existing test suite, or Git repository in the current project directory. The proposed public conversation-core seam was presented during the preceding spec discussion; protocol and hardware checks supplement it without replacing it.
- **Still requiring implementation verification:** exact STT/wake/LLM models, recognizer streaming capability, legal terms, model/runtime compatibility, German quality thresholds, wake calibration, recognition-completion allowance, delivered-speech tracking precision, KDE activation/lock/mute integration, acoustic voice-stop reliability, resource usage, and measured latency. These are validation tasks, not silently settled hardware claims.
- **Delivery gate:** M0–M4 gates apply to the documented activation mode. Manual activation is sufficient for the MVP activation gate; hands-free operation and speaker capabilities require their own evidence. Clean install/run/test/health instructions must reproduce the supported setup on a fresh CachyOS user account. Future M5 work is separately scoped and is not implied by this spec.
- **Tracker state:** The local tracker marks this spec ready-for-agent, meaning its implementation direction is specified. This status does not mean code exists, hardware validation passed, or all P0 requirements are fulfilled.
